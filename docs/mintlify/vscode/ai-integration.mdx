## Overview

The VS Code extension runs a local [Model Context Protocol](https://modelcontextprotocol.io/) server for AI-assisted GLua development. It works with VS Code chat and other MCP-compatible agents.

The server combines three parts of your development environment:

- A selected server debugger for control and execution
- Captured server and client console output and runtime errors
- Runtime Lua errors and GLuaLS language diagnostics

<Warning>
`execute_lua` can change game state. Only connect agents you trust, and only install `gm_rdb` on development servers.
</Warning>

## Available tools

The server intentionally exposes only five tools:

| Tool | Description |
|---|---|
| `execute_lua` | Evaluate inline code like a live REPL, run a workspace Lua file, or manually refresh a file |
| `run_console_command` | Run one command in the Garry's Mod server console |
| `read_console` | Read filtered, timestamped console lines, optionally after a previous cursor and observation window |
| `get_errors` | Read filtered in-game runtime errors |
| `get_issues` | Read filtered GLuaLS language-server errors and warnings |

## Debugger connections and routing

`gluals_gmod` is the server-control debugger connection. `execute_lua`, workspace file execution, `lua_refresh_file`, and `run_console_command` require a connected server debugger.

`gluals_gmod_client` provides client telemetry and paused debugging. It does not provide custom MCP client control. MCP `client` and `shared` Lua still dispatch through the selected server debugger's net broadcast.

Mutation tools accept an optional `sessionId`:

- With exactly one connected server, MCP selects it automatically.
- With no connected server, MCP returns a server-required capability error.
- With multiple connected servers, supply the intended server `sessionId`.
- Client and terminated session IDs are rejected for mutations.

Mutation results identify the selected target session. The active debug-session dropdown in VS Code does not choose the MCP target.

`get_issues` reads static GLuaLS diagnostics and is independent of runtime debugger sessions.

For inline execution, supply `code`. Inline source is limited to 256 KiB in UTF-8. For a file, supply `file`; the debugger sends the path rather than putting the file contents in the MCP request, so the inline limit does not apply. Server files execute directly. Client/shared file payloads use bounded chunked net messages and can be up to 1 MiB. The file must be inside a workspace `lua/` directory.

`execute_lua` is designed for quick experiments and active debugging, similar to a REPL against the running game. Inline server/shared execution returns a bounded summary of server return values plus console lines and errors observed immediately after dispatch. That observed context is best-effort and can include unrelated game activity. Pass the returned cursor to `read_console` and `get_errors` for later or paged results, especially for asynchronous client code, hooks, and timers.

Choose the execution realm explicitly:

| Realm | Where the Lua runs |
|---|---|
| `server` | Only the connected Garry's Mod server |
| `client` | Every client currently connected to that server, not one selected client |
| `shared` | The server and every connected client |

<Warning>
The debugger bridge broadcasts `client` and `shared` execution to every player connected to the selected development server. The tool rejects those realms unless the request explicitly sets `confirmClientBroadcast` to `true`. This option means "I understand this runs clientside on all connected clients"; it does not target one client. Use the `server` realm unless you intend to run the code on every connected client.
</Warning>

A client debugger is not required to dispatch a client/shared broadcast. Without an attached client telemetry session, the agent cannot observe that client's prints or errors. A `gluals_gmod_client` session observes only the client it is attached to, not every client that received the broadcast.

`run_console_command` always targets the server console. It accepts one command, rejects semicolon chaining, and never invokes a command on clients. Console commands have the same ability to mutate or stop the development server as commands entered manually.

The runtime tools require the [debugger](/debugger/setup). `get_issues` can return language diagnostics without a running game.

## Auto-refresh and files

Garry's Mod normally reruns eligible Lua files as soon as you save them. Agents should not call `execute_lua` merely to rerun every edited file, because that can execute initialization code twice.

Auto-refresh primarily covers files automatically loaded by gamemodes, `autorun`, effects, entities, and weapons. Dynamic `include` or `AddCSLuaFile` patterns and some base-file relationships may not refresh automatically.

Use file execution modes deliberately:

| Request | When to use it |
|---|---|
| `{ "file": "...", "action": "execute", "realm": "server" }` | Explicitly run a file for the first time or rerun a file that is not auto-loaded |
| `{ "file": "...", "action": "refresh" }` | Force Garry's Mod's `lua_refresh_file` behavior after auto-refresh did not apply or trigger |

`action` defaults to `execute`. Execute actions require `realm`. `refresh` only accepts a file, not inline code, and lets Garry's Mod determine the affected realm through `lua_refresh_file`.

## Limit returned context

All read tools use small defaults and bounded responses. Narrow the request before increasing its limit:

| Tool | Useful controls |
|---|---|
| `read_console` | `lines`, `cursor`, `observeMs`, `sessionId`, `realm`, `source`, `contains`, `includeSessions` |
| `get_errors` | `source`, `sessionId`, `realm`, `cursor`, `minCount`, `contains`, `includeStackTrace`, `limit`, `includeSessions` |
| `get_issues` | `severity`, `path`, `code`, `contains`, `offset`, `limit` |

`get_errors` defaults to runtime errors whose source is `lua` and omits stack traces. Set `source` to `console`, `debugger`, or `all` only when those domains are relevant. `get_issues` never includes runtime errors.

`read_console` and `get_errors` accept an optional `sessionId` and filter telemetry by `realm: "server"` or `realm: "client"`. `shared` is execution-only and is not a telemetry filter. Each telemetry record keeps its session attribution and current session state. Set `includeSessions` to `true` when the response should also include the compact available-session inventory; retained terminated-session records are marked as terminated so they remain distinguishable from connected sessions.

Runtime reads return `truncated` when more matching data exists or fields were shortened. Cursored reads also return `dropped` when the requested cursor is older than the retained ring buffer, so an agent does not silently mistake an incomplete history for a complete one.

For repeated console reads, pass the `cursor` from the previous `read_console` response to return only newer lines. Set `observeMs` to wait for the requested window before reading when output is asynchronous. The maximum is 30 seconds and the default is `0`, so existing reads remain immediate.

## Connect from VS Code

VS Code discovers the GLuaLS MCP server automatically. Open the chat tool picker and enable **GLuaLS Garry's Mod Runtime**. You do not need to configure a separate Copilot integration.

## Connect another AI agent

<Steps>
  <Step title="Start GLuaLS in VS Code">
    Open your GLua workspace in VS Code. The extension hosts the MCP server because it owns the debugger connection and language diagnostics.
  </Step>
  <Step title="Copy the connection configuration">
    Run **GLuaLS: MCP: Copy Server Configuration** from the Command Palette. The command copies the current Streamable HTTP URL and bearer token.
  </Step>
  <Step title="Add it to your agent">
    Paste the copied server entry into your agent's MCP configuration. The exact outer property can vary between clients; the copied object uses VS Code's `servers` format.
  </Step>
  <Step title="Connect the debugger">
    Start a `gluals_gmod` server debug session before asking the agent to execute Lua. Attach `gluals_gmod_client` separately when you need telemetry or paused debugging for one client.
  </Step>
</Steps>

The copied entry has this shape:

```json
{
  "servers": {
    "gluals-gmod": {
      "type": "http",
      "url": "http://127.0.0.1:21113/mcp",
      "headers": {
        "Authorization": "Bearer <generated-token>"
      }
    }
  }
}
```

## Security

The MCP server:

- Binds only to `127.0.0.1`
- Requires a bearer token for every request
- Stores its generated token in VS Code secret storage
- Validates host and origin headers to prevent DNS rebinding
- Rate-limits requests and bounds request/output sizes
- Marks game output as untrusted runtime data in tool responses

## Settings

| Setting | Default | Description |
|---|---|---|
| `gluals.gmod.mcp.enabled` | `true` | Start the local MCP server |
| `gluals.gmod.mcp.port` | `21113` | Streamable HTTP port. `0` chooses an available port |
| `gluals.gmod.mcp.rateLimitPerMinute` | `120` | Maximum MCP requests per minute for each local client |

If you set the port to `0`, copy a new external-agent configuration after each extension restart because the ephemeral URL can change.
